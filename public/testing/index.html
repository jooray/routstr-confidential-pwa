1. What this is

A routstr node normally sees everything you send to the AI model and everything it answers. In confidential mode the node only relays encrypted traffic between you and the provider (Venice, for now). It cannot read your prompt or the answer, and you never get the node's provider API key. Zero-knowledge proofs make sure neither side cheats, and you pay for the usage the provider itself reported.

This guide covers protocol v3. A connection to the provider can now carry several requests: over HTTP/2 the expensive setup runs once and later messages reuse it. Over HTTP/1.1 every request gets its own connection. None of this is merged into upstream Routstr yet, so every step below uses forks (see the branch map).

Background reading, all on GitHub:

  • The paper (PDF): the guarantees and the two-party handshake.
  • One-pager (PDF): the short version for users.
  • What changed from v2 to v3 (PDF).
  • PROTOCOL-V3.md: the full specification.

2. End users: the web app

Nothing to install. The app does all the cryptography in your browser.

Get started

  1. Open jooray.github.io/routstr-confidential-pwa. The default node is https://routstr.cypherpunk.today, which runs protocol v3 since 2026-11-12 (HTTP/2 and HTTP/1.1, a connection deposit of 2 sats). The header should say offer verified: the app checked the node's signed price list against the node key it has pinned.
  2. Fund it in the Wallet panel. You have three options:
    • Lightning: enter an amount in sats (500 is filled in) and press Lightning. Pay the invoice (QR code or copy). Once it is paid, the node creates a key for you, or tops up the one you have. Your wallet may add a routing fee.
    • Pay with Cashu: paste a cashuA… or cashuB… token and press Create key (or Top up). The panel lists the mints the node accepts and any mint fee.
    • Use an existing key: paste an sk-… key you already have on this node.
    The key lives only in this tab unless you tick Remember on this device under Your key. Copy it somewhere if you leave money on it. Withdraw (refund) returns the whole balance as a Cashu token or to a Lightning address.
  3. Pick a model, type a message and send it.

Reading the result

Under each answer there is a line like this:

verified  HTTP/2 · #2  kept connection  first token 0.6 s  total 1.4 s  21/48 tok  0.04 sat  [details]
PartMeaning
verifiedEvery check passed: the provider's certificate, the proofs, the node's signed receipt, and a cost within the signed prices. If a check fails you get an error here instead.
HTTP/2 · #2 or HTTP/1.1How the browser talked to the provider (the "framing"). With HTTP/2, #2 is the request's number on its connection.
new / kept / prepared connectionnew: this message opened a connection (slow, about 18 MB of setup data). kept: it reused an open HTTP/2 connection (fast). prepared: it used a connection the app had set up ahead (see pre-warming below).
tokens and costFrom the signed receipt.

Press details to open the Verification panel. It shows the provider's certificate chain, the proofs (π_NK, π_WIN, π_C3S), and the Receipt card: usage, cost, the session fee, the connection deposit and what happened to it, and the connection row (the first characters of the connection id sid and the request number n). The full signed receipt JSON is at the bottom of that card. A timeline shows where the time went.

HTTP/2 or HTTP/1.1

Open the Node panel and find HTTP to the provider: auto (HTTP/2 when the node offers it), HTTP/2 only, or HTTP/1.1 (HTTP/2 off). The pill in the header shows what your next message will use.

  • HTTP/2: one connection serves your next messages until the node closes it after its idle time. Later answers start in under a second. The cost is that the provider can tell those messages come from one client. It can already do that for everything sent with one API key.
  • HTTP/1.1: every message opens its own connection. Slower, and no two messages share a connection.

If HTTP/2 fails to open on a node, the app uses HTTP/1.1 for that node for 10 minutes and tells you so.

The connection deposit

Opening a connection costs the node real bandwidth before you have sent anything. So the node holds a small connection deposit when a connection opens (the Node panel and the Costs panel show the amount).

  • The first answer on that connection gives it back. The receipt says so.
  • The node keeps it if the connection ends with no answer through your doing: a prepared connection you never used, a message you stopped before it reached the provider, or a failed proof.
  • You get it back if the node, its sidecar or the provider failed.

Pre-warming (Costs panel, Keep a connection prepared) is off by default: on HTTP/2 the open connection already stays warm between messages, for about two minutes of idle. When you turn it on, after your first answer the app prepares one connection in the background while the page is visible, so the next message after a pause is fast. An unused prepared connection costs its deposit. The app does not pre-warm when the deposit is above 5 sats, on a metered connection, or when your balance cannot cover the deposit plus one message.

Images

Switch to Image mode above the message box. Pick a model, resolution, aspect ratio and count. The node sees the model, the resolution and the count, because it charges for those. It does not see the prompt or the image. The price is a flat amount per image from the signed offer. Images are kept in this browser's storage with their prompt, so delete them from the gallery when you are done. For vision models, the Image button in chat mode attaches a picture to your message. That picture is sent inside the encrypted request, too.

To try another node, open the Node panel, set the node URL, its key (hex or npub) and the trusted provider host, then press Apply. Defaults goes back to routstr.cypherpunk.today.

Report problems as GitHub issues on jooray/routstr-confidential. See what to include.

The app protects you from the node, not from whoever serves the page. The footer shows the app and library commits, and version.json lists a hash over every file. Keep balances small.

3. End users: routstrd, for any app

routstrd is a local daemon with an OpenAI-compatible API on http://127.0.0.1:8008/v1. Any app that can set a base URL and one extra header can use confidential mode through it. For now you have to build it from source, together with the SDK and two helper programs.

You need: git, Bun, Node.js with npm, and Rust through rustup (the repository pins its toolchain, 1.97.1, and rustup fetches it).

Build

Put the three checkouts next to each other. The SDK link below relies on that.

mkdir confidential && cd confidential

# 1. The helper programs cu-prover and cu-2pc (they must be from the same release as the node's sidecar)
git clone -b main https://github.com/jooray/routstr-confidential
(cd routstr-confidential/crypto && \
  cargo build --release -p zkbench --bin cu-prover -p twopc --bin cu-2pc)
# result: routstr-confidential/crypto/zkbench/target/release/cu-prover and cu-2pc

# 2. The SDK with the confidential transport (not on npm yet)
git clone -b confidential-2pc https://github.com/jooray/routstr-sdk
(cd routstr-sdk && npm install && npm run build)

# 3. routstrd, built against that SDK
git clone -b confidential-upstream https://github.com/jooray/routstrd
cd routstrd
bun install
rm -rf node_modules/@routstr/sdk && ln -s "$PWD/../routstr-sdk" node_modules/@routstr/sdk
bun run build       # after the link, so dist/ bundles the SDK
bun link            # installs `routstrd` into ~/.bun/bin (put it on your PATH)

The binaries land in crypto/zkbench/target/release/, not in crypto/target (the repository sets that build directory). Keep cu-prover and cu-2pc in one directory: the SDK looks for cu-2pc next to cu-prover, or in CU_2PC_BIN / CU_2PC. Without the SDK link the daemon fails at startup with an Export named … not found error. After you update either checkout, run npm run build in routstr-sdk, then bun run build in routstrd.

Fund and configure

routstrd onboard
routstrd receive <cashu token>    # or: routstrd receive 1000   (a Lightning invoice for 1000 sats to pay)

Then add this block to ~/.routstrd/config.json (keep the keys that are already there):

"confidentialUpstream": {
  "enabled": true,
  "trusted_hosts": ["api.venice.ai"],
  "node_pubkeys": ["2ca46ee98f3134c4e11a638663a45983b590bfdefd31588f9c2f03455fba15e7"],
  "prover_path": "/absolute/path/to/routstr-confidential/crypto/zkbench/target/release/cu-prover",
  "http": "auto",
  "maxConnectionDepositMsat": 100000,
  "http2": { "reuse": "per-client" },
  "prewarm": { "enabled": true }
}
KeyDefaultMeaning
trusted_hosts(none)Provider hostnames whose TLS certificate you accept. Empty refuses every session.
node_pubkeys(from Nostr)Node keys whose signed offers you accept. The key above is routstr.cypherpunk.today's. Without this list, routstrd only trusts a key that announced the node on Nostr and has a review.
prover_pathCU_PROVER_BIN, CU_PROVER, PATHWhere cu-prover is.
httpautoauto takes the node's first choice and falls back to HTTP/1.1 for 10 minutes if HTTP/2 fails to open. "2" or "1.1" uses only that. "1.1" turns HTTP/2 off.
maxConnectionDepositMsat100000The largest connection deposit you accept. A node that asks for more is not used.
http2.reuseper-clientWhich requests may share an HTTP/2 connection: per-client (one local API key), shared (everything this daemon sends to that node), or none (a connection per request).
prewarm.enabledtruePrepare a connection ahead while you are sending requests. An unused one costs its deposit. It only pre-warms nodes whose deposit is at most prewarm.maxDepositMsat (5000).

More keys (http2.maxConnections, prewarm.maxTotal, …) are in routstrd's docs/confidential-upstream.md.

Run and send a request

routstrd start                                            # restart it after editing config.json
# optional: pin every request to one node
routstrd start --provider https://routstr.cypherpunk.today

curl -i http://127.0.0.1:8008/v1/chat/completions \
  -H 'content-type: application/json' \
  -H 'x-routstr-verify: confidential' \
  -d '{"model":"deepseek-v4-flash","max_tokens":200,"stream":true,
       "messages":[{"role":"user","content":"Say hi in three words."}]}'

Pick a model the node lists in its offer (https://routstr.cypherpunk.today/v1/confidential/offer?v=3, the price_list keys). max_tokens is required. With the header, a request is either confidential or refused; it never goes out in the clear. Only POST /v1/chat/completions and the image endpoints (/v1/images/generations, /v1/image/generate) work this way. With the OpenAI Python client: default_headers={"x-routstr-verify": "confidential"}.

The response headers tell you what happened:

  • x-routstr-confidential-http: the framing, 2 or 1.1.
  • x-routstr-confidential-connection: new, armed (prepared) or reused, and the request's number on its connection.

A stream sends its final data: [DONE] only after the receipt and proofs check out. If a check fails, the stream ends with an error and no [DONE].

Reuse scopes

Requests on one HTTP/2 connection are linkable for the provider. With the default per-client, everything sent with one local API key can be linked that way, across conversations. To narrow it:

  • Send x-routstr-reuse-scope: <any string up to 256 bytes>, for example one value per conversation. Requests with different scopes never share a connection. The header can only narrow sharing.
  • Set "http2": {"reuse": "none"} for a connection per request.
  • Set "http": "1.1" to turn HTTP/2 off for confidential requests.

Logs

routstrd logs -n 50                                  # today's log
routstrd logs -f                                     # follow
grep '\[confidential\]' ~/.routstrd/logs/$(date +%F).log

Each confidential request writes one line, [confidential] request {...}, with the framing, what it found (cold, armed or open connection), time to first token and bytes each way. It holds no content or credentials. Other lines to look for:

  • node_protocol_outdated: <node> offers routstr-confidential v2 …: that node is not upgraded and is skipped. If no other node can serve the request, you get a 502 with error_type: "node_protocol_outdated".
  • upgrade_required: the node is newer than your routstrd. Pull and rebuild.
  • twopc_version_mismatch: your cu-2pc and the node's sidecar are from different releases. Rebuild the helpers from main.
  • framing "2" marked bad: HTTP/2 failed to open, so that node uses HTTP/1.1 for 10 minutes.
  • retiring armed … unused …; its deposit of N msat is charged: a prepared connection was never used.

Set ROUTSTRD_LOG_LEVEL=debug before routstrd start for more detail. routstrd never writes confidential prompts or answers to its request/response log.

4. Developers

4a. The browser library

routstr-confidential-web is what the web app uses. The cryptography runs as WebAssembly in a Web Worker. The built wasm is committed, so you do not need Rust. Install it from git and pin a commit: 

npm install github:jooray/routstr-confidential-web#<commit on main>

npm builds dist/ on install. In Vite, set worker: { format: "es" } and optimizeDeps: { exclude: ["@routstr/confidential-web"] }. Your page's CSP needs script-src 'self' 'wasm-unsafe-eval', worker-src 'self', and connect-src for the node (https: and wss:). The web app's vite.config.ts is a working example. 

import { createConfidentialClient } from "@routstr/confidential-web";

const client = createConfidentialClient({
  node: "https://routstr.cypherpunk.today",
  nodePubkeys: ["2ca46ee98f3134c4e11a638663a45983b590bfdefd31588f9c2f03455fba15e7"],
  trustedHosts: ["api.venice.ai"],
  credential: "sk-…",                 // or client.setCredential(...) later
  http: "auto",                       // "2", or "1.1" (HTTP/2 off); client.setHttp(...) later
  prewarm: true,
  onEvent: (e) => console.debug(e),   // progress events, never secrets
});

const stream = await client.chat.completions.create({
  model: "deepseek-v4-flash",
  messages: [{ role: "user", content: "Hello" }],
  max_tokens: 512,
  stream: true,
});
for await (const chunk of stream) out.textContent += chunk.choices[0]?.delta?.content ?? "";
const v = await stream.verification;  // throws if any proof or receipt check failed
console.log(v.framing, v.n, v.connection, v.deposit, v.ttftMs, v.receipt.cost_msats);

The main options:

OptionDefaultMeaning
http"auto"The node's first framing, with a fallback from HTTP/2 to HTTP/1.1. "2" or "1.1" forces one.
reuseScopeone scope per credentialRequests with different scopes never share a connection, so the provider cannot link them that way.
http2.reuse"shared""none" opens a connection per request.
maxConnectionDepositMsat100000The largest connection deposit accepted. More is refused before anything is sent.
padBucketoffPad the request body to a multiple of N bytes, or "pow2". It hides the exact size from network observers and the provider, not from the node, which learns the token count at settlement. It costs upload.
prewarmofftrue or options (maxDepositMsat, default 5000; allowMetered). Keeps one prepared connection while the page is visible and funded.
onNodeProtocolOutdatedCalled when the node's offer names an older protocol.

What stream.verification resolves to (the main fields):

FieldMeaning
sid, nThe connection id and the request's number on it.
framing, stream, fellBack"2" or "1.1"; the HTTP/2 stream; whether HTTP/2 failed and it fell back.
connection"new", "armed" or "reused".
receipt, receiptJson, receiptSigThe node-signed receipt.
receiptSigOk, attestationSigOk, usageMatch, costWithinOfferThe checks. All are true, or the call would have thrown.
costMsats, ownUsageWhat you paid, and the usage the client decrypted itself.
depositThe connection deposit and whether this request released it.
providerThe certificate chain, TLS version, cipher suite and ALPN.
http, ttftMs, timingsThe provider's status, the time to first token, and per-step timings and proof results.

Typed errors to handle: NodeProtocolOutdatedError (a v2 node), UpgradeRequiredError (the node is newer), TwoPcVersionMismatchError, ConnectionDepositError, RequestRefusedError (402 balance, 409 offer changed). Images: client.images.generate({...}). The library README has the rest, including the security model of serving this code from a web page.

4b. The SDK (Node and Bun)

The routstr SDK has the same client for Node and Bun. It runs cu-prover and cu-2pc as child processes. Build it from the confidential-2pc branch as in section 3, then depend on your local checkout (for example npm install /path/to/routstr-sdk).

A single request, without routing:

import { fetchConfidential } from "@routstr/sdk/bun";   // or "@routstr/sdk/node"

const res = await fetchConfidential({
  baseUrl: "https://routstr.cypherpunk.today",
  bearer: "sk-…",
  body: { model: "deepseek-v4-flash", max_tokens: 200, stream: true,
          messages: [{ role: "user", content: "Hello" }] },
  options: {
    trustedHosts: ["api.venice.ai"],
    nodePubkeys: ["2ca46ee98f3134c4e11a638663a45983b590bfdefd31588f9c2f03455fba15e7"],
    proverPath: "/path/to/cu-prover",   // cu-2pc next to it, or twoPcPath / CU_2PC
    http: "auto",
  },
  reuseScope: "conversation-1",          // optional
});
// read res.body as a normal SSE stream, then:
const { costMsats } = await (res as any).confidentialSettled;
console.log(res.headers.get("x-routstr-confidential-http"), res.headers.get("x-routstr-confidential-connection"));

With routing, node selection and top-ups, pass the same options as confidential: {...} to routeRequests (from @routstr/sdk/bun or /node); RoutstrClient then runs fetchConfidential in place of fetch(). Details: client/confidential/README.md in the SDK. To test against a node you run: CU_PROVER=… CU_2PC=… bun scripts/confidential-v3-e2e.ts <node> <sk-key> <model>.

5. Node operators

A confidential node is a normal Routstr node plus cu-sidecar, a small Rust service. The sidecar holds the provider key, relays the TLS connection to the provider, writes the one record that carries the key, and verifies the client's proofs. Billing uses the node's normal reservation and settlement.

What you need

  • An API key for an OpenAI-compatible provider that you are willing to sell. Venice is the tested one; see Providers for others.
  • A server with a public HTTPS name and a reverse proxy that passes WebSockets.
  • The node: jooray/routstr-core, branch confidential-2pc.
  • The sidecar: jooray/routstr-confidential, branch main. Build it with podman/docker or with Rust.
  • Python 3 with OpenSSL 1.1.1 or later, for the provider check.

1. Check your provider

Confidential mode needs a provider that behaves in specific ways (it waits for the full body, uses the last duplicate JSON key, enforces token caps, reports usage in the stream, and more). Check yours with the offer file you will deploy. The key goes only to the offer's upstream_host. 

cd routstr-confidential
T=crypto/tools/provider-profile-check.py
python3 -I $T --offer my-offer.json --key-env MY_PROVIDER_KEY --model <a cheap chat model>          # A1-A13: all must pass
python3 -I $T --offer my-offer.json --key-env MY_PROVIDER_KEY --model <same> --h2                  # H1-H8: before you offer HTTP/2
python3 -I $T --offer my-offer.json --key-env MY_PROVIDER_KEY --image-model <model> --images       # I1-I9: before you offer images

The --h2 run idles a connection for h2.idle_secs (5 minutes by default) and ends with a verdict: offer "2": yes, no, because … (keep HTTP/1.1 only), or not yet (run it again). The image run generates three paid images.

2. The sidecar offer file

Start from crypto/relay/offer.venice.json. It has the host, the request-head template, the chat block (the pinned suffix), the HTTP framings and the image endpoint. The file carries no prices: models and prices come from the node. 

"http": ["2", "1.1"],
"h2": {"probe_path": "/api/v1/models", "max_requests": 100, "max_lifetime_s": 3600,
       "idle_secs": 300, "kinds": ["chat", "images"]}
FieldDefaultMeaning
http["1.1"]Framings in your order of preference. Add "2" only after --h2 said yes. Keep "1.1" after it: clients fall back to it.
h2.probe_pathA cheap authenticated GET (the models list). It runs once per connection and stores the key in the provider's header table.
h2.max_requests100Requests per connection (1 to 1000).
h2.max_lifetime_s3600A connection closes at the first settlement after this long.
h2.idle_secs300The sidecar's idle limit. Not longer than the idle time your --h2 run passed with.
h2.kinds["chat"]Add "images" to serve images on HTTP/2 (needs endpoints.images).
endpoints.imagesThe image endpoint (Venice: POST /api/v1/image/generate, count_key "variants"). Without it the node offers chat only.
model_allowlistempty (all)Restrict the confidential models.

For another provider, see docs/SETUP.md and docs/CHAT-SUFFIX.md in routstr-confidential. The sidecar refuses at startup a chat block that clients would refuse.

3. Build and run the sidecar

# container
podman build -f crypto/Containerfile.sidecar -t cu-sidecar crypto      # or docker
openssl rand -hex 32     # the shared token: CU_SIDECAR_TOKEN here, CONFIDENTIAL_SIDECAR_TOKEN on the node
podman run -d --name cu-sidecar --network <node network> \
  -e UPSTREAM_API_KEY=… -e CU_SIDECAR_TOKEN=… \
  -v ./my-offer.json:/etc/cu-sidecar/offer.json:ro \
  cu-sidecar \
  --listen 0.0.0.0:7444 --upstream api.venice.ai:443 --key-env UPSTREAM_API_KEY \
  --offer /etc/cu-sidecar/offer.json --node-settles --runs-dir /runs

# or with cargo (binary in crypto/zkbench/target/release/cu-sidecar)
cd crypto && cargo build --release -p cu-sidecar
  • Never publish the sidecar's port. It does not check client credentials (the node does that before it connects), so anyone who reaches it spends your provider key. Off loopback it refuses to start without the token. The token crosses the node-to-sidecar link in cleartext: keep that link on loopback or a private container network, or tunnel it.
  • The image ships Venice's offer file at /etc/cu-sidecar/offer.json. Mount your own over it if you changed anything.
  • Limits: --max-sessions 32 connections, --max-body 8 MiB per request. Run files are kept 24 hours (--runs-keep-hours, 0 removes them at once).
  • After 5 HTTP/2 connections in a row fail to open, the sidecar stops offering "2" for 10 minutes and logs framing "2" withdrawn from the offer. If that repeats, run --h2 again.

4. The node

Build routstr-core from confidential-2pc (its Dockerfile is the upstream one, or uv sync for a source checkout) and set:

CONFIDENTIAL_SIDECAR_URL=http://cu-sidecar:7444
CONFIDENTIAL_SIDECAR_TOKEN=<the sidecar's CU_SIDECAR_TOKEN>
CORS_ORIGINS=https://jooray.github.io,https://your-app.example     # comma-separated, not JSON

Start it with a long WebSocket ping timeout and one worker:

uvicorn routstr:fastapi_app --host 0.0.0.0 --port 8000 --proxy-headers \
  --ws-ping-interval 20 --ws-ping-timeout 300
  • Use this instead of the image's default fastapi run routstr. On a slow link the keepalive waits behind about 16 MB of setup data, and the default 20 s timeout drops the connection. Do not set --ws-max-size below 12 MiB.
  • The node keeps offers and sessions per process. It refuses to start in confidential mode with more than one worker.
  • The sidecar URL and token are read only from the environment. The other settings below are stored in the database at first start; after that, change them in the admin settings (PATCH /admin/api/settings) or the dashboard.
  • Your reverse proxy must pass WebSockets for /v1/confidential/ws and /v1/confidential/zk (Upgrade/Connection headers, a read timeout of a few minutes).
  • CORS_ORIGINS must allow the origins of browser clients, or the web app cannot reach your node. The default is *. Like other settings, a value already in the database wins over the environment.
  • The provider row must have the type venice (add it in the dashboard as a Venice provider). A row seeded from UPSTREAM_BASE_URL has the type custom, and then the offer lists no models. On a scratch test node with SQLite you can fix it directly: delete from upstream_providers where base_url not like '%venice%'; update upstream_providers set provider_type='venice'; then restart.
SettingDefaultEffect
CONFIDENTIAL_CONNECTION_DEPOSIT_MSATmax(abandon fee, session fee, 1000)Held when a connection opens, released by its first settled request, kept when the client wastes the connection. 0 = no deposit.
CONFIDENTIAL_IDLE_TIMEOUT_S120Close a connection with no request in flight after this long. At least 10, at most h2.idle_secs.
CONFIDENTIAL_MAX_ACTIVE_PER_IP16Connections per client address. At the limit the longest-idle used one is closed, otherwise the setup gets 429.
CONFIDENTIAL_MAX_UNUSED_PER_IP12Unused connections per client address (prepared ones count).
CONFIDENTIAL_TRUSTED_PROXIESnonePeers whose client-address header is believed, e.g. 127.0.0.1,::1 for nginx on the same host. Without it, all clients behind your proxy share one limit.
CONFIDENTIAL_SESSION_FEE_MSAT0A flat fee, once per connection, with its first settled request.
CONFIDENTIAL_ABANDON_FEE_MSATthe session feeFor a request dropped before it reached the provider, and for most provider 4xx refusals.
CONFIDENTIAL_RATE_SURCHARGE_PCT0Added to the per-token rates and image prices.
CONFIDENTIAL_RESERVE_MARGIN_TOKENS16Completion tokens reserved beyond max_tokens.

Each connection costs the node about 18 MB of upload and under 0.5 s of CPU, before any request. Size the deposit to that. All of these values go into the signed offer, so clients see them before they pay.

5. Check and test

curl -s 'https://<node>/v1/confidential/offer?v=3' | jq '{v, http, h2, twopc,
  connection_deposit_msat, idle_timeout_s, upstream_host, models: (.price_list|keys)}'

v must be 3, twopc "split-public-1", http what your offer file lists, and models not empty.

The reference driver (in crypto/client, after npm install there; it needs cu-prover and cu-2pc):

cd crypto/client && npm install
CU_PROVER=../zkbench/target/release/cu-prover CU_2PC=../zkbench/target/release/cu-2pc \
  node --experimental-strip-types src/driver.ts --node https://<node> --node-pubkey <hex or npub> \
  --model <model> --max-tokens 40 --http 2 --requests 3 --auth <sk-… or cashu…>
# then the same with --http 1.1

It prints every check. The gates run against your provider key and spend a little money:

Both exit non-zero on any deviation. CU_KEY_ENV, CU_UPSTREAM and CU_V3_OFFER point them at another provider. CU_NO_IMAGES=1 skips the paid image cases.

With the web app: open the Node panel, enter your node URL, its key and the provider host, press Apply, fund and send a message. If the app cannot reach the node, check CORS_ORIGINS first.

6. Announcing, or not

A node with a sidecar configured adds the tag ["confidential","3"] to its Nostr listing, so clients can find confidential nodes. A test node should not announce itself. Point RELAYS at a relay that does not exist (for example RELAYS=ws://127.0.0.1:9), and stop test nodes when you are done. A forgotten node with real relays keeps announcing itself.

Upgrading from v2: upgrade the sidecar and the node together. v2 clients then get 426 upgrade_required. See "Upgrading from v2" in docs/SETUP.md.

7. Reporting problems

Open an issue at github.com/jooray/routstr-confidential/issues. Include:

  • Versions. Web app: the app and library versions and commits from the footer. routstrd, SDK, helpers: the commit of each checkout (git rev-parse --short HEAD). Node operators: the routstr-core and sidecar commits.
  • The node URL, and the offer's v and http.
  • The framing (HTTP/2 or HTTP/1.1) and what the request found (new, kept/reused, prepared/armed).
  • The receipt's sid and n (Receipt card, connection row; or the receipt JSON). With these the operator can find the session in the logs.
  • The exact error text, and for routstrd the [confidential] log lines around it.
  • Browser and OS, or Bun/Node version. Your link speed, if the problem is slowness.
Never post your sk- key, Cashu tokens, provider API keys, node nsecs, the sidecar token, or your prompts. The receipt JSON is safe to share. It holds usage and costs, no content.
